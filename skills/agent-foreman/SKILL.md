# 派活监工

你（Claude）写交代书，用监督脚本把活派给执行的 agent，盯进度、回答它的提问，最后看实物验收。下文的 `<本技能目录>` 指本技能所在目录（加载技能时给出的 Base directory），脚本是其中的 `scripts/foreman.mjs`。

## 分工

- **你（Claude）**：创意方向、理解用户意图、产品取舍、审美、查清原因和定方案、验收标准、与用户沟通、看实物验收。
- **Codex**（主力执行者）：方案定好后的一切落地，包括细节设计、编码与测试、源码阅读与调研（也包括为定方案先做的调研）、图片/媒体生成、数据处理、打包。
- **DSH**（可选，本机装了 DSH CLI 才有）：主要做**前端 UI 设计**，包括页面和组件的视觉设计、布局、样式、交互外观，以及把它们实现成前端界面代码。用同一个脚本加 `--agent dsh` 派给它，默认 DeepSeek-V4.1-Flash + 高档推理。其他活都优先交给 Codex；Codex 任务里遇到前端 UI 设计的部分，会按运行约定自己派给 DSH 子任务。审美和验收仍由你判，流程和总把控和 Codex 完全一样。
- **Antigravity**（可选，本机装了 agy CLI 才有）：用户点名时才派。用同一个脚本加 `--agent agy`，默认用 Orchestrator (Carbon)（型号 `gemini-pro-orchestrator`，没有推理档位可选）；用户点名别的模型时才换，例如 `--model hydrogen` / `argon` / `carbon` 按 `--effort` 取该系列最新版。Orchestrator 类型的模型可以自己派子代理并行做（子代理用什么模型由它定；运行约定要求子代理先读原始交代、往 progress.log 记进度），其他 Antigravity 模型不派子代理。只用选定的模型：额度用完或找不到它时任务直接失败并写明原因，不自动换模型，也不自动换执行者；你报告用户，由用户决定改派给谁。流程和总把控和 Codex 完全一样。
- 你只直接改协调性文件（项目规则、方案、交代书、技能文档）。执行者前面不加任何传话 Agent，由你直接调用监督脚本。

## 流程

1. **先想清楚**：创意、取舍、文案、数值由你定。用户没表态的产品问题先问用户，再派活。
2. **写交代书**：复制 `brief-template.md`，每个槽位都填。目标、实际场景、开发者意图、项目意图、验收标准这五栏是防止做偏的根本，任何一栏写不出来，说明还没想清楚，先想清楚或问用户，再派活。「原因与方案」按下面「交到哪一级」由你先查清、定好。子代理（Codex 派出的 DSH 或 terra）由运行约定要求直接读原始交代书，不靠转述。
3. **启动**（在 Monitor 工具里运行，`timeout_ms: 1800000`）：
   ```bash
   node <本技能目录>/scripts/foreman.mjs start <task> --cd <工作目录> 2>&1 <<'EOF'
   …交代书全文…
   EOF
   ```
   **模型**：一般不写 `--model`，即 Codex 主力 sol 系列最新版 + 高档推理。任务里要操作电脑界面的部分（computer use：点按软件界面、操作桌面应用，包括 Blender 建模），由主 Codex 派 terra 系列最新版的子代理完成，主模型不来回切换。这条要求由脚本自动附在运行约定里，交代书不用写。用户要求时才用 `--model best`。
   task 名全局唯一：`<项目简称>-<主题>-<两位序号>`，如 `商城-购物车-01`、`官网-首页改版-02`；不能有空格、引号、斜杠，最长 40 个字。终端底栏、状态条和推送里都显示这个名字。每条事件都会实时推送给你。Monitor 最长 30 分钟，但到期只结束跟踪，任务照常运行：监督进程启动后由系统托管。跟踪满 29 分钟会以退出码 8 自动交回，最后一行给出继续跟踪的命令，照着在 Monitor 里重新运行 `watch <task>` 即可；收到 Monitor 到期通知时同样处理。
4. **处理事件**：执行者阻塞提问时跟踪命令以退出码 7 结束，最后三行是问题摘要、完整问题路径和回答命令——按下一节回答后，再用 Monitor 运行 `watch <task>` 接着跟踪；不阻塞的 ❓ 不会结束跟踪，有空就回答。⚠ ⏸ ✖ ❌ 先看原因再决定重试、改交代还是报告用户；⏱ 是单轮跑满 `--max-min` 被叫停，不算失败：先看它做到哪了，再用 `send` 让它从断点接着做，剩下的活太大就拆成更小的关卡；✅ 带着执行者的回复原文，进入验收。
5. **看实物验收**：先看代码实现（改了哪里、取值从哪来、是否按原因和方案改），再测实际表现：界面截图或真机、视频抽帧、音频测量、自己跑测试。执行者说完成不等于验收通过。逐条复核回复里的「我自己做的决定」。哪些由你判、哪些可让执行者查，见下面「审查分工」。
6. **返工 / 下一关**：`send <task>` 加 heredoc，写清具体改哪里、改成什么。
7. **汇报**：测试结果与实物验收分开报告，失败照实说。

## 和其他技能的关系（统一约束，其他技能无需适配）

- **分工**：领域技能（视频、网站、数据……）规定做什么、按什么流程、达到什么标准；本技能规定谁来做、怎么交出去、按多大一块交。两者冲突时，执行方式以本技能为准，内容和标准以领域技能为准。
- **领域技能里任何调用 Codex 的写法**（裸跑 `codex exec`、「交给 Codex」等）都改为通过本技能的监督脚本执行。原命令里的提示词、参考图、参数照搬进交代书，不必修改领域技能本身。
- **交代书引用领域技能**：写明执行者要读哪些技能文档（绝对路径，如 `~/.claude/skills/<技能>/references/<文件>.md`），它能直接读；只摘录关键决定，不整篇复制。
- **Codex 的工具和你一样**：它加载用户的 MCP 和插件，领域技能里用到的接口它也能调用，不要因为「它接不上」就自己做。

## 派活颗粒度

- **你直接做**：所有判断与创意；一两步就完成的零碎操作（查一个状态、改一个名字、读一个文件）。写交代书比亲手做还慢的，不派。
- **交给执行者**：目标明确、步骤多、要循环处理很多项、要等待或轮询、要生成或下载的落地工作。
- **按「批」派，不按「项」派**：一批是一组你会一起验收的产出，例如一层资产、一个模块、一轮修改，不要一张图、一个节点派一次。一个任务控制在 5～40 分钟，再大就拆成关卡。每批交回一个能一眼验收的东西：联系表、清单、测试日志、截图。
- **独占资源**：同一时间只能有一方修改的东西（一张画布、一份在线文档、一个数据库、同一块代码），在交代书「范围」里写明由这个任务独占。它运行期间，你不改、也不派别的任务去改。
- **付费、对外、不可逆的操作**（付费生成、发布、发消息、删除）：一律先得到用户批准。执行者默认不开沙箱、工具调用不需要审批，能拦住它的只有交代书：「必须先问的地方」要列出这些操作，执行者遇到时提问或停下，不能自己决定。

## 交到哪一级

默认**方案级**：派活之前，你先把原因查清、把方案定好，再交出去。修复和新功能都一样。

- **原因和方案由你定**：修复要定位到具体原因，不只转述现象。性能问题先录 CPU（例如 CDP Profiler）定位到具体函数；显示或数据对不上，先读代码找到各处取值的来源。方案写到改哪些地方、用什么做法，技术选型也在这里定。交代书写清五栏、「原因与方案」，以及所有用户看得到的决定（文案、数值、交互、审美、产品取舍），写到能照做。执行者只决定具体怎么写代码，并在回复的「我自己做的决定」里逐条交代，你复核。
- **方案要先调研才定得下来时**：第一关只交调研结果和方案建议，不写代码。方案建议要写清打算怎么做、改哪些地方、为什么不用更简单的做法、有什么风险。你定了再放行实施。新加存储、依赖或抽象，改核心结构或接口，不可逆的迁移，有几种做法且代价差别大，这几类方案一律由你定，不让执行者边做边定。
- **写到具体步骤**：只在你确切知道怎么做时，例如把你写好的文案接进去、纯机械的改名搬迁。其他情况不规定写法：你猜的步骤不一定对，还会挡住执行者自己的判断。
- **执行者派子代理时同样按这条**，运行约定已经告诉它。做的过程中发现交代书没预见的上述大改动，运行约定要求它先提问再动手。

## 审查分工

执行者可以帮你查，但「通过不通过」只能由你判。

- **必须你亲自判断**：执行者产出的最终验收；审美、创意、文案语气、节奏；是否符合用户意图、产品取舍；审查中的判断题，例如某条算不算问题、该放哪一层、要不要改；要给用户看或要公开的东西。
- **可以交给执行者查**：自己产出的自检（测试、规格、数值）；大量逐条比对，例如迁移有没有漏、文档和代码是否一致、全量链接或尺寸检查；可测量的指标，例如响度、帧、分辨率。
- **执行者只交疑点，不下结论**：审查类交代书要求输出「疑点清单 + 证据（文件:行号、截图、数值）」，不写「通过 / 不通过」。你对每条疑点逐一裁决；高严重度的亲自复核，再抽查几处它说没问题的地方，防止漏报。
- **不让做的人审自己**：复核用新开的任务，不在产出它的同一会话里自查了事。

## 并行

推进时优先并行：能拆开的事用 worktree 或不同分支隔离开发，验收后合并，bug 也可以并行修；但不要为了并行而并行。派活前先判断能不能拆，先读 `parallel.md`（判断标准、隔离方式、一次最多几个、验收和合并）。

## 裁决总原则：从大局取舍

执行者交回的一切——结论、疑点、提问、「我自己做的决定」——你都先回到这件事的原始意图再判断：用户要解决什么问题、产品原本怎么设计（交代书的「目标」「实际场景」「开发者意图」「项目意图」）。

1. **先问影不影响目标**：会改变用户看到的结果、核心体验或产品方向的，认真处理；只是细节分支、不影响目标的，按最简单且符合意图的做法当场定掉，或者明确放下，不为它开新一轮调查或返工。
2. **把方向拉回来**：执行者连续在边角情况上提问或打转时，不逐条陪它深挖。重申目标，砍掉范围外的部分，给出默认做法，让它继续往主线推进。
3. **取舍由你做，并写清理由**：不要把不影响意图的细节选择推回给用户，也不要为了面面俱到而扩大范围。
4. **返工要朝着目标收敛**：每一轮返工都必须更接近原始意图；不影响目标的小瑕疵直接接受，列为已知小问题，不无限打磨。

## 回答执行者的提问

- 能从用户已表达的意图推出答案的：`answer <task> [编号]` 加 heredoc，直接给决定和理由。
- 涉及产品范围、用户能看到的取舍、删除或不可逆操作，而用户没表态的：先问用户，再回答。执行者等不到会停在这个问题上，之后用 `send` 把用户的决定发过去。不要为了不让它停下而替用户拍板。
- 执行者工作中途想补充要求：`note <task>` 留言，它每做完一步会查看。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 交代书只写范围，不写已定的决定 | 写具体数值、文案原文、交互细节和理由 |
| 把执行者的完成声明当验收 | 看实物，自己复跑关键检查 |
| 把执行者的复核「没问题」当结论 | 只当疑点清单，逐条裁决，再抽查它说没问题的地方 |
| 被执行者的疑点和提问带进细节分支，一轮轮深挖 | 回到原始意图：影响目标的才处理，不影响的当场定掉或放下 |
| 自己动手写代码或跑生成 | 交给执行者；你只改协调性文件 |
| 用 sleep 轮询进度 | 等 Monitor 推送的事件 |
| 在执行者前面加子 Agent 转述 | 直接调用监督脚本 |
| 回复缺「我自己做的决定」 | 让它补上，并逐条复核 |
| 交代书只转述现象，没查原因、没定方案；或者替执行者写好每一步写法 | 先查清原因、定好方案（改哪里、用什么做法），具体写法交给它；方案定不下来，先设调研关 |
| 工作区有别人未提交的改动却没交代 | 在交代书「范围」里写明保留，禁止 stash / reset |

不确定命令、选项、退出码、事件符号或遇到异常时，再读 `reference.md`。
