# 并行派活

## 原则

推进时优先并行：能拆开的事，用 worktree 隔离开发后合并，或者不同内容走不同分支后合并，bug 也可以并行修。但不要为了并行而并行。拆之前先过下面的判断，拆不开就老老实实串行。

## 什么时候并行

同时满足才并行：

- **互不依赖**：一件事不用等另一件的结果，接口和产品决定已经定好。
- **改动不重叠**：不是同一批文件、同一段逻辑，合并时不会打架。
- **值得拆**：每一块都够大（大约 10 分钟以上的活）。省下的时间要多于写交代书、验收和合并多花的时间。

**这些情况串行**：有先后依赖；方向或设计还没定；都要改同一块核心代码；要独占同一个资源（同一张画布、数据库、端口、运行中的客户端、同一台测试机）；验收必须看整体效果，分开看不出好坏；零碎小改。

**并行修 bug**：先把 bug 复现、定位，按根因分组。根因不同、改动模块不同的各开一个任务；同一根因的合成一个任务，不要拆开重复修。原因还没查清时，可以先并行调查，定位后再决定怎么修。

## 怎么隔离

- **不同目录**：互不相干的目录，直接用 `--cd` 划开。任务默认不开沙箱，防止互相覆盖靠隔离的目录和交代书「范围」，每轮结束脚本会报告工作目录外的新改动，验收时要看。
- **同一个 git 仓库**：每件事一条分支、一个 worktree，由你在派活前建好，`--cd` 指向它。分支名写清内容，如 `fix/登录超时`、`feat/素材卡筛选`。基于同一个最新提交开始。
- **没有 git 的目录**：拆不开就串行。
- 交代书「范围」写明本任务的分支和 worktree、不能碰的文件，以及另外几个任务在改什么。要 Codex 提交时明确写「在本分支提交」，没写它不会提交。
- 项目对 worktree 的依赖安装有自己的规矩时，照项目文档做，写进交代书。pnpm 项目不要让 worktree 软链主仓库的 `node_modules` 后再运行 pnpm，会改坏主仓库的链接。

## 怎么运行

- 每件事一个 task 名、一份交代书，各自在自己的 Monitor 里 `start`。
- **一次最多 3 个 Codex**：再多会撞上模型限流（看到 ⚠ 繁忙或断线就先减少并行数）。装了 DSH 时，前端 UI 设计的部分另外用 `--agent dsh` 派给它，它走自己的额度，不占 Codex 名额。本机渲染和测试会抢资源，你也要看得过来，所有代理同时在跑的总数一般不超过 5 个，事情更多时分批。
- **提问按任务名回答**：每个任务的 ❓ 和退出码 7 各自独立，`answer <task>` 时核对 task 名。

## 怎么验收和合并

1. **逐个验收**：每条分支单独过验收，不合格的返工，不带进主线。
2. **合并由你负责**：逐条合进主线，先合最小、风险最低的。每合一条先看 `git diff` 范围对不对，有冲突就读懂两边的意图再解决，拿不准的交给 Codex 新开任务处理，你来裁决。
3. **合并后整体验证**：全部合完再跑一次测试和实物联调，分开都通过不等于合起来没问题。
4. **保护现场**：主线工作区有别的会话未提交的改动时，不 stash、不 reset。和要合并的文件重叠就先停下，告诉用户。合并只在本地，推送由用户决定。
5. **收尾**：合并验证后删除对应的 worktree 和分支，不留一堆旧副本。
